## Motivação: o salto de 20 para 40

O problema desta aula:

> Dados $n \le 40$ itens com pesos inteiros $w_i \le 10^9$ e uma capacidade $C$, qual é a **maior soma de pesos** de um subconjunto que não passa de $C$?

Um exemplo pequeno: pesos $5, 9, 13, 4, 7, 11$ e $C = 30$. A melhor escolha é $\{5, 9, 4, 11\}$, com soma **29**. Nenhum subconjunto soma exatamente 30.

Na aula de busca completa, $n \le 20$ deixava testar os $2^{20} \approx 10^6$ subconjuntos. Agora $n$ vai até 40, e $2^{40} \approx 1{,}1 \cdot 10^{12}$. Testar todos levaria horas.

A observação que salva: $2^{40} = 2^{20} \cdot 2^{20}$. Todo subconjunto dos 40 itens é **um subconjunto dos 20 primeiros** junto com **um subconjunto dos 20 últimos**. Se listarmos as somas de cada metade separadamente (só $2^{20}$ de cada lado), o problema vira "escolha uma soma de cada lista". E isso dá para fazer **sem** testar todos os pares de somas.

## A ideia, no exemplo pequeno

Divida os 6 pesos em duas metades: $A = \{5, 9, 13\}$ e $B = \{4, 7, 11\}$.

**Passo 1: listar as somas de cada metade.** Cada metade tem 3 itens, então $2^3 = 8$ subconjuntos:

| Subconjunto de $A$ | Soma | | Subconjunto de $B$ | Soma |
|---|---|---|---|---|
| $\{\}$ | 0 | | $\{\}$ | 0 |
| $\{5\}$ | 5 | | $\{4\}$ | 4 |
| $\{9\}$ | 9 | | $\{7\}$ | 7 |
| $\{5, 9\}$ | 14 | | $\{4, 7\}$ | 11 |
| $\{13\}$ | 13 | | $\{11\}$ | 11 |
| $\{5, 13\}$ | 18 | | $\{4, 11\}$ | 15 |
| $\{9, 13\}$ | 22 | | $\{7, 11\}$ | 18 |
| $\{5, 9, 13\}$ | 27 | | $\{4, 7, 11\}$ | 22 |

**Passo 2: ordenar uma das listas.** As somas de $B$, em ordem: $0, 4, 7, 11, 11, 15, 18, 22$.

**Passo 3: combinar.** Para cada soma $x$ de $A$, o melhor parceiro em $B$ é **a maior soma $y$ que não passa de $C - x$**:

| $x$ (de $A$) | Espaço que sobra: $30 - x$ | Maior $y$ de $B$ que cabe | $x + y$ |
|---|---|---|---|
| 0 | 30 | 22 | 22 |
| 5 | 25 | 22 | 27 |
| 9 | 21 | 18 | 27 |
| 14 | 16 | 15 | **29** |
| 13 | 17 | 15 | 28 |
| 18 | 12 | 11 | **29** |
| 22 | 8 | 7 | **29** |
| 27 | 3 | 0 | 27 |

O máximo da última coluna é **29**. A linha do $x = 14$ corresponde a $\{5, 9\}$ de $A$ com $\{4, 11\}$ de $B$ (soma 15), exatamente o $\{5, 9, 4, 11\}$ da motivação.

Repare no que **não** fizemos: não testamos os $8 \cdot 8 = 64$ pares de somas. Para cada $x$, olhamos uma posição só na lista ordenada de $B$.

<Callout type="tente">
Por que não dá para pegar simplesmente a melhor soma de $A$ e a melhor soma de $B$ separadamente e juntar as duas?

<details>
<summary>Ver resposta</summary>

Porque a restrição $x + y \le C$ amarra as duas escolhas. A melhor soma de $A$ que não passa de 30 é 27, e a de $B$ é 22, mas $27 + 22 = 49$ não cabe. Quanto sobra para $B$ depende do que você escolheu em $A$. Por isso o passo 3 procura o parceiro **para cada** $x$.

</details>
</Callout>

### Achando "o maior $y$ que cabe" sem percorrer a lista

Na lista ordenada de $B$, o maior $y \le C - x$ é o elemento **logo antes** do primeiro elemento maior que $C - x$. A função `upper_bound` da STL acha esse "primeiro elemento maior" numa lista ordenada em $O(\log)$ passos (você vai ver como ela funciona por dentro no milestone 3):

| Índice | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| somas de $B$ ordenadas | 0 | 4 | 7 | 11 | 11 | 15 | 18 | 22 |

Para $x = 9$, sobram $30 - 9 = 21$. O primeiro elemento maior que 21 é o 22, no índice 7, então o melhor parceiro é o do índice 6: **18**. Isso confere com a tabela acima.

### Gerando as somas de uma metade

Um jeito curto de listar as somas é **dobrar a lista** a cada item. Comece com $\{0\}$ (o subconjunto vazio) e, para cada peso $w$, acrescente uma cópia de todas as somas que já existem, agora somadas com $w$. Para $A = \{5, 9, 13\}$:

| Depois de processar | Somas na lista | Tamanho |
|---|---|---|
| (nada) | 0 | 1 |
| 5 | 0, **5** | 2 |
| 9 | 0, 5, **9, 14** | 4 |
| 13 | 0, 5, 9, 14, **13, 18, 22, 27** | 8 |

Em negrito estão as somas novas de cada passo: as antigas mais o peso atual. A lista dobra de tamanho a cada item, então depois de $k$ itens tem $2^k$ somas, uma por subconjunto.

## Generalizando

Com $n$ itens, cada metade tem cerca de $n/2$ itens e $2^{n/2}$ somas. Os três passos custam:

$$
\underbrace{O\!\left(2^{n/2}\right)}_{\text{gerar as somas}} + \underbrace{O\!\left(2^{n/2} \cdot n\right)}_{\text{ordenar } B} + \underbrace{O\!\left(2^{n/2} \cdot n\right)}_{\text{uma busca por } x} = O\!\left(2^{n/2} \cdot n\right)
$$

Ordenar uma lista de tamanho $m$ custa $m \log_2 m$, e aqui $\log_2 2^{n/2} = n/2$. Cada uma das $2^{n/2}$ buscas custa $\log_2 2^{n/2} = n/2$ passos. Com $n = 40$, o total é cerca de $2 \cdot 10^7$ operações, contra $10^{12}$ da força bruta.

<MitmDiagram />

<Callout type="dica" title="O padrão geral">
Meet in the middle serve quando a resposta é uma **combinação de uma escolha de cada metade** e, para cada escolha da esquerda, dá para achar rápido a melhor (ou contar as compatíveis) da direita. "Rápido" geralmente significa ordenar uma das listas e buscar nela.
</Callout>

## Código: o problema da motivação

Duas sintaxes de C++ novas aparecem aqui:

- `const vector<long long>& w` passa o vetor **por referência** (o `&`), sem copiá-lo, e o `const` promete que a função não vai alterá-lo;
- `for (long long x : A)` percorre cada elemento de `A`, chamando-o de `x` a cada volta.

```cpp
#include <bits/stdc++.h>
using namespace std;

// Somas de todos os subconjuntos de w[l..r-1], dobrando a lista a cada item.
vector<long long> todas_as_somas(const vector<long long>& w, int l, int r) {
    vector<long long> somas;
    somas.push_back(0);                          // o subconjunto vazio
    for (int i = l; i < r; i++) {
        int tamanho = somas.size();              // quantas somas existiam antes de w[i]
        for (int j = 0; j < tamanho; j++)
            somas.push_back(somas[j] + w[i]);    // cada subconjunto antigo, agora com w[i]
    }
    return somas;
}

int main() {
    int n;
    long long C;
    cin >> n >> C;
    vector<long long> w(n);
    for (int i = 0; i < n; i++) cin >> w[i];

    vector<long long> A = todas_as_somas(w, 0, n / 2);
    vector<long long> B = todas_as_somas(w, n / 2, n);
    sort(B.begin(), B.end());                    // só B precisa estar ordenada

    long long melhor = 0;                        // o subconjunto vazio sempre vale
    for (long long x : A) {
        if (x > C) continue;                     // essa metade sozinha já não cabe
        // índice do primeiro elemento de B maior que C - x
        int pos = upper_bound(B.begin(), B.end(), C - x) - B.begin();
        // B[pos - 1] é o maior elemento <= C - x (pos >= 1, porque B[0] = 0 <= C - x)
        melhor = max(melhor, x + B[pos - 1]);
    }
    cout << melhor << "\n";
}
```

**Entrada:**

```
6 30
5 9 13 4 7 11
```

**Saída:**

```
29
```

O programa faz exatamente a tabela do passo 3: para cada uma das 8 somas de $A$, uma busca nas 8 somas ordenadas de $B$.

- **Tempo:** $O(2^{n/2} \cdot n)$.
- **Memória:** $O(2^{n/2})$. Com $n = 40$, são duas listas de $2^{20}$ `long long`, cerca de 16 MB.

### O mesmo código no formato de contest

Com o template (`ll` = `long long`, `rep` = laço `for`, `pb` = `push_back`, `sz(x)` = tamanho como `int`, `all(x)` = `x.begin(), x.end()`):

```cpp
#include <bits/stdc++.h>
using namespace std;
typedef long long ll;
#define rep(i,a,b) for(int i=(a);i<(b);i++)
#define all(x) (x).begin(),(x).end()
#define pb push_back
#define sz(x) (int)(x).size()
void fastio(){ ios::sync_with_stdio(false); cin.tie(nullptr); }

vector<ll> somas(const vector<ll>& w, int l, int r) {
    vector<ll> s = {0};
    rep(i, l, r) { int t = sz(s); rep(j, 0, t) s.pb(s[j] + w[i]); }
    return s;
}

int main(){
    fastio();
    int n; ll C;
    cin >> n >> C;
    vector<ll> w(n);
    rep(i, 0, n) cin >> w[i];
    vector<ll> A = somas(w, 0, n / 2), B = somas(w, n / 2, n);
    sort(all(B));
    ll melhor = 0;
    for (ll x : A) if (x <= C) melhor = max(melhor, x + *prev(upper_bound(all(B), C - x)));
    cout << melhor << "\n";
}
```

Aqui `*prev(upper_bound(...))` faz o mesmo que `B[pos - 1]`: `prev` volta uma posição e `*` lê o valor.

## Variação: contar em vez de maximizar

Muitos problemas pedem **quantos** subconjuntos somam exatamente $x$. A estrutura é a mesma: para cada soma $a$ de $A$, conte quantas vezes $x - a$ aparece em $B$. E aqui mora a principal armadilha da técnica.

<Callout type="tente">
Pesos $2, 2, 2, 2$ e $x = 4$. Quantos subconjuntos (de posições) somam 4? Divida em $A = \{2, 2\}$ e $B = \{2, 2\}$ e confira se "para cada $a$, perguntar **se** $4 - a$ existe em $B$" dá a resposta certa.

<details>
<summary>Ver resposta</summary>

A resposta certa é **6**: qualquer par de posições dentre as 4 ($\binom{4}{2} = 6$).

As somas de cada metade são $0, 2, 2, 4$: o 2 aparece **duas vezes**, porque "só o primeiro 2" e "só o segundo 2" são subconjuntos diferentes. Contando direito:

| $a$ | procura $4 - a$ | vezes que aparece em $B$ |
|---|---|---|
| 0 | 4 | 1 |
| 2 | 2 | 2 |
| 2 | 2 | 2 |
| 4 | 0 | 1 |

Total: $1 + 2 + 2 + 1 = 6$. Se você só pergunta "existe?" (com `binary_search`), cada linha conta no máximo 1 e o total dá **4**, errado.

</details>
</Callout>

Para contar as repetições numa lista ordenada, use `upper_bound(...) - lower_bound(...)`: `lower_bound` aponta para o primeiro elemento $\ge v$ e `upper_bound` para o primeiro $> v$, então a diferença é quantos são iguais a $v$.

## Armadilhas comuns

<Callout type="armadilha" title="Somas repetidas são subconjuntos diferentes">
Ao **contar**, cada ocorrência de uma soma em $B$ é um subconjunto diferente e conta separado. `binary_search` só diz se existe; use `upper_bound - lower_bound`.
</Callout>

- **Somas e contagens em `int`.** Vinte pesos de $10^9$ somam $2 \cdot 10^{10}$, e o número de subconjuntos pode chegar a $2^{40}$. Os dois precisam de `long long`.
- **Ordenar a lista errada.** A busca é feita em $B$, então é $B$ que precisa estar ordenada. Iterar sobre $A$ pode ser em qualquer ordem.
- **Gerar as somas com recursão que copia vetores.** É muito mais lento que dobrar a lista; com $2^{20}$ itens, isso pesa.

<details class="para-depois">
<summary>Para depois: alternativas e detalhes de implementação</summary>

**Two pointers em vez de busca binária.** Com $A$ e $B$ ordenadas, à medida que $x$ cresce, o limite $C - x$ diminui, então o ponteiro em $B$ só anda para trás. Isso troca o $\log$ da busca por um passo constante amortizado (milestone 5).

**`unordered_map` para contar.** Funciona na teoria, mas tem constante alta, e testes adversariais podem forçar colisões e dar TLE. Ordenar e buscar é mais seguro.

**$n$ ímpar.** As metades têm tamanhos $\lfloor n/2 \rfloor$ e $\lceil n/2 \rceil$, e a lista maior tem $2^{\lceil n/2 \rceil}$ itens. Ajuste as estimativas de memória.

**`reserve`.** Chamar `somas.reserve(1 << k)` antes de gerar evita realocações do vetor durante o dobramento. É uma otimização de constante, não de complexidade.

</details>
